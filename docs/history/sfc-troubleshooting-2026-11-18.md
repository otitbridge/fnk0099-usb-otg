# SFC列挙失敗の調査経過（2026-11-18）

前日までの経過は[2026-11-17の履歴](sfc-troubleshooting-2026-11-17.md)にあります。各節は、その試行時点での判断と実機の状態です。現在の状態と再開時の注意は、[引き継ぎ資料](../sfc-troubleshooting.md)を先に参照してください。

## 回復処理の試作：ルートポート電源の入れ直し

SFCを挿したまま起動すると列挙に失敗します。そこで、Host側で詰まりを検出してルートポートを切断・再接続する処理を、試作ブランチ `proto/sfc-port-recovery`（ローカルのみ・未統合）に作りました。主ブランチのソースは変更していません。

ESP-IDF 5.5.0のソースで、次の3点を確認しました。

- 列挙が取り消されても、失敗した機器オブジェクトは機器が消えるまで解放されず、`usb_host_lib_info().num_devices` に数えられたまま残る（`components/usb/enum.c:849-880`、`usbh.c:1054-1061`）。
- 構成済みの機器だけを数える `usb_host_device_addr_list_fill` と比べれば、詰まりを検出できる（`usbh.c:802-848`）。
- ルートポートの電源オフは、DWC内部のポート電源ビットを下げるだけで、VBUSは切らない（`usb_host.c:728-738`、`hub.c:646-663`、`hcd_dwc.c:1202-1216`）。

試作 `rcv1-pp`（コミット `c77386c`）の動作は次のとおりです。

- 有効にするのは `CONFIG_FNK0099_HOST_RECOVERY` のときだけ。既存のログ行は変えていない。
- 機器はあるのに構成済みの機器がなく、NEW_DEVもない状態が2秒続いたら、電源をオフにする。
- 機器が解放されるのを待ち、100・500・2000ms保持してから電源をオンにする。
- 再試行は1接続あたり3回まで。
- 判断ロジックは純粋なCの状態機械として分け、ホストテスト（15シナリオ・4,972チェック、ASan/UBSan）に合格した。ビルドは警告0、アプリのSHA-256は `653e6d39…` です。

書き込みの手順は次のとおりです。

1. 実機の0x0〜0x5DFFFが元の退避と全バイト一致することを照合する。
2. アプリ領域0x10000だけを書き込む。
3. 版を替えるときは、退避を書き戻し、全範囲を読み戻して照合する。

[試作と段階1の記録](../evidence/sfc-root-port-recovery-prototype-2026-11-18.json)。

| 試験 | 条件 | 結果 |
|---|---|---|
| K0 | 現行Host、UARTリセットで起動（当日の対照） | 660msに `CHECK_ADDR` で失敗 |
| T2-1〜5 | 試作版、UARTリセットで起動 | **0/5で回復せず**。601msに失敗した後、電源オフで毎回すぐ機器が解放された（`flags=0x2`）。しかし再接続しても、3回とも `CHECK_SHORT_DEV_DESC` で失敗し、12.5秒で諦めた |
| T4 | 諦めた後、リセットしない接続で観測し、実際に抜き差し | 通常どおり再認識し、右・Bを受信。回復処理は動かない |
| T0 | SFCなしで60秒 | 回復処理の動作は0回、エラーなし |
| T1 | Host起動後に挿す | 通常どおり認識し、右・B・Aを受信。回復処理は動かない |
| T3-1〜3 | 電源を完全に切ってから起動 | 3/3が初回で認識（671msに機器、771msに受信開始）。回復処理は動かない |

**判定：ポート電源の入れ直しは、VBUSを切らなくても機構としては働く（切断を検出し、機器を解放する）。しかし、UARTリセットで起動したときの失敗は回復しない。** 通常の抜き差し、Host先行接続、SFCなしの動作は壊していません。

## 最初の列挙を始める時刻の比較

T3で試作版が3/3だった一方、前日の現行Hostは1/3でした。そこで、電源を切ってからの起動を同じ日・同じ手順で比べました。順番は、試作版3回 → 現行版5回 → 試作版5回です。現行版の5回は1/5で、A07-5では660msの `CHECK_ADDR` を捉えました。試作版は5/5でした。

試作版の回復処理は8回とも動いておらず、最初の列挙がそのまま成功しています。試作版では、USBイベント処理タスクを作る前に `RECOVERY enabled` のログを1行出すため、Hostの処理開始が約10ms遅れます（heartbeatが290ms→301ms）。

意図して遅らせる版 `rcv1-pp-d1000`（コミット `721f972`）も作りました。`root_port_unpowered` でインストールし、起動後1,155msにルートポートへ給電します。ビルドは警告0、SHA-256は `89256b2b…` です。[時刻比較の記録](../evidence/sfc-first-enumeration-timing-2026-11-18.json)。

| 版 | 最初の列挙 | 電源を切ってから起動 | UARTリセットで起動 |
|---|---|---|---|
| 現行 `07e005a` | 約0.6秒 | 2/8（前日1/3、当日1/5） | 0/8 |
| 試作 `rcv1-pp` | 約10ms遅い | 8/8 | 0/5 |
| 遅延 `rcv1-pp-d1000` | 約1.5秒 | **5/5** | **5/5** |

遅延版は10回とも同じ流れでした。1,155msに給電し、1,771msに `DEVICE 1209:d004`、1,871msに `keyboard start: ESP_OK`。電源を切った起動では、右・Bも受信しています。警告・パニック・取得中の再起動はありません。

**判定：この1台目・C to Cの条件では、成否は最初の列挙を始める時刻で決まっていた。** 起動後約0.6秒で最初の要求を送ると失敗しやすく、一度失敗するとSFCはその後のバスリセットに応答しなくなります。約1.5秒まで遅らせると、どちらの起動条件でも10/10で認識しました。

約0.6秒の時点でSFCの準備ができていない理由は、まだ確定していません。候補は、ESP32のリセット中のUSB-Serial-JTAGのD+プルアップ、UIAPduinoのブートローダーからアプリへの切り替えなどです。必要な最小の遅延、2台目、旧ケーブル、遅延版での回帰試験は未実施です。

FNK0099は現在、試作の遅延版 `rcv1-pp-d1000` のアプリで動いています（ブートローダーとパーティションは07e005a）。主ブランチのビルドではありません。1台目は挿したまま認識しています。

## 遅延版の回帰確認：段階1〜3に合格

遅延版 `rcv1-pp-d1000` で、従来の回帰項目を1台目・C to Cで確認しました。

- R1〜R3：SFCを挿したままUARTリセットで起動し、1回の取得で続けて確認した。
- R4：SFCを抜いた状態で、改めて起動した。

[回帰確認の記録](../evidence/sfc-delayed-enumeration-regression-2026-11-18.json)。

| 項目 | 結果 |
|---|---|
| R1 起動時の認識 | 1,771msに `DEVICE 1209:d004`、1,871msに `keyboard start: ESP_OK`、全解放を受信 |
| R1 12ボタン | B → Y → SELECT → START → 上 → 下 → 左 → 右 → A → X → L → R の24遷移。離すたびに0x000へ戻った |
| R1 保持 | 左35.51秒・右33.38秒。保持中にマスクの変化なし |
| R1 同時押しと一部だけ離す | 右＋Y＋B（0x083）を4.61秒 → Bだけ離す（0x082）→ 右＋Yを4.91秒 → 全部離す（0x000） |
| R2 押したまま抜く | 抜いた瞬間は右に上が混ざっていた（0x090）。抜いた時点で `reason=disconnect` により0x000。挿し直すと `DEVICE address=2` で認識し、右・Bを受信 |
| R3 物理RESET×3 | 3/3。毎回1,155msに給電、1,771msに機器、1,871msに受信開始。リセットのたびに右・Bを受信 |
| R4 SFCなしで起動してから挿す | 空のポートに給電しただけで、回復処理は動かずエラーもない。約35秒後に挿すと通常どおり認識し、右・B・Aを受信 |

R2で抜いた瞬間に、E行が1件出ました（`USB HOST: EP command error: ESP_ERR_INVALID_STATE`）。HIDの切断処理は `ESP_OK` で終わり、挿し直しにも影響はありませんでした。原因はまだ調べていません。それ以外に、警告・パニック・想定外の再起動・回復処理の動作はありません。

**判定：最初の列挙を約1.15秒遅らせた試作版で、1台目はHID 1.1.0の回帰項目（段階1〜3）に合格した。** ただし、確かめたのは1台目とC to Cケーブルだけで、各項目は1回（RESETは3回）です。2台目・旧ケーブル・より短い遅延・主ブランチへの取り込みは、まだ行っていません。

## 遅延版を2台目と旧ケーブルで確認：12/12で認識

1台目を旧ケーブル構成につなぎ替えることはできなかったため、2台目（公開v1.0.0、SELECT=Tab固定）で確かめました。順番は、C to C → 旧ケーブル構成（USB-C to USB-Aケーブル＋USB-A to USB-C変換アダプタ）です。FNK0099は遅延版 `rcv1-pp-d1000` のままで、書き込みはしていません。各ケーブルで、UARTリセット起動×3（操作なし）と電源断起動×3（約20秒後に右・B）を行いました。[2台目・ケーブル別の記録](../evidence/sfc-delayed-enumeration-controller2-cables-2026-11-18.json)。

| 2台目のケーブル | UARTリセットで起動 | 電源を切ってから起動 |
|---|---|---|
| C to C（1台目と同じケーブル） | 3/3 | 3/3（電源オフ13.1〜17.5秒）。右・Bを受信 |
| 旧ケーブル構成 | 3/3 | 3/3（電源オフ20.4〜21.5秒）。右・Bを受信 |

12回とも1台目と同じタイミングでした。1,155msに給電、1,771msに `DEVICE 1209:d004`、1,871msに `keyboard start: ESP_OK`、1,881msに全解放を受信しています。起動時の警告・エラー・パニック・回復処理の動作はありません。

補足が2つあります。
- 旧ケーブルの3回目では、Bが約0.4秒の間に3回押されて離された記録になっていました（押していた時間は20・290・50ms）。軽く押した場合か、2台目のBボタンの接点のばたつきの可能性がありますが、調べていません。
- ケーブルを交換するために、キーボードを開いたまま2台目を抜きました。このときも、1台目のR2と同じE行1件（`USB HOST: EP command error: ESP_ERR_INVALID_STATE`）が出ました。その後の切断処理は正常に完了しています。

**判定：遅延の効果は、試した範囲では個体やケーブルによらない。** 遅延版は、1台目・C to C（電源断5/5・UARTリセット5/5・物理RESET 3/3）と、2台目のC to C・旧ケーブル（12/12）で、SFCを挿したままの起動をすべて認識しました。11-17には、2台目も旧ケーブル構成も、遅延なしでは失敗していました。

1台目＋旧ケーブル、当日の現行Hostでの対照、より短い遅延、主ブランチへの取り込みは、まだ行っていません。現在のFNK0099は遅延版のままで、2台目を旧ケーブル構成で接続しています。
